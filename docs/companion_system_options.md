# 동료(파티 멤버) 시스템 설계 옵션

> 작성일: 2026-09-02
> 성격: **사전 조사 리포트 — 구현 없음.** Part 2 이후 유서프의 동료 합류를 전제로,
> 현재 코드 구조 위에 얹을 수 있는 선택지를 정리한다.

---

## 0. 먼저: 기존 결정과 충돌한다

`docs/part1_story_script_draft.md:620` 「동료 시스템 관련 정리 (2026-08-30)」에 이런 결정이 남아 있다:

> 유서프가 사막/유적 씬에 계속 등장하는 건 실제 파티/동료 시스템이 필요한 게 아님 — 카밀·나딤처럼
> 해당 씬에 배치된 NPC로서 스토리 플래그에 따라 대사만 치는 방식이면 충분함(전투 참여나 조작 가능한
> 동료 아님). 그러니 "동료 시스템을 만들어야 하나"는 고민 안 해도 됨 — 지금 구조 그대로 가능.

이 결정은 코드 주석에도 박혀 있다 — `npc/yusuf_desert_npc.gd:7` "실제 파티 시스템 없이 사막 씬에
배치된 NPC로만 존재한다(동료 시스템 불필요 — 문서 결정사항)".

이번 검토는 그 결정을 **재검토하는 것**이다. 아래 A안을 고르면 기존 결정이 유지되고, B/C안을 고르면
위 두 곳(문서 + 주석)이 stale해지므로 같이 갱신해야 한다.

한편 서사적으로는 이미 합류 직전까지 와 있다 — 유적 시퀀스에서 유서프는 계속 곁에 있고,
`part1_story_script_draft.md:733`에서 "이번엔 나도 도망 안 쳐. 끝까지 같이 가자"로 마무리된다.
즉 **"같이 다닌다"는 이미 대사로 성립했고, 남은 건 그걸 시스템으로 얼마나 표현할 것인가**다.

## 1. 현재 구조 파악

### 1-1. 가장 중요한 사실: 플레이어에겐 "전투 개체" 객체가 없다

몬스터는 제대로 된 개체 클래스를 갖는다 — `battle/monster_state.gd`의 `MonsterState`:

```
index / monster_type / monster_data / variant / max_hp / hp /
resistance(EnemyResistance) / status(StatusEffects) / mana / display_name / rewarded
+ is_alive() / take_damage() / heal() / can_attack() / recover() ...
```

반면 **플레이어는 그런 객체가 없고, 상태가 전부 `GameState.flags` 딕셔너리의 납작한 키로 흩어져 있다**
(`systems/game_state.gd:96` `DEFAULT_FLAGS`):

```
"player_hp": 25, "player_base_max_hp": 25, "player_max_hp": 25,
"player_mana": 20, "player_max_mana": 20, "player_level": 1, "player_xp": 0,
"equipped_sword": "", "equipped_staff": "", "equipped_shield": "", ...
```

`battle_turn_manager.gd:10-14`가 이 분담을 명시적으로 못 박아 두었다 — "플레이어 HP/마나는 GameState.flags,
몬스터 상태는 매니저의 monsters 배열". 즉 **적 진영은 이미 다개체 구조, 아군 진영은 단일 개체 하드코딩**이라는
비대칭이 현재 구조의 핵심이고, 동료 시스템 난이도를 좌우하는 것도 결국 이 지점이다.

### 1-2. 전투: 규칙 엔진과 연출이 분리돼 있다

| 레이어 | 파일 | 역할 |
|---|---|---|
| 규칙 | `battle/battle_turn_manager.gd` (707줄) | 턴 진행, 카드 효과, 피해 계산, 적 행동, 승패 판정 |
| 연출/입력 | `battle/battle_scene.gd` (3,653줄) | 스프라이트/VFX/HP바/버튼, 타겟 선택 UI |
| 데이터 | `card.gd`, `battle_data.gd`, `cards/*.tres` | 카드 정의, 몬스터 스탯 |

분리 자체는 좋은 상태다. 규칙에 동료를 넣는 것과 연출에 동료를 넣는 것을 **따로 견적낼 수 있다.**

동료 관점에서 걸리는 구체적 지점:

- **적 턴이 피격 대상을 하드코딩한다.** `battle_turn_manager.gd:661`이 곧바로 `GameState.damage_player()`를
  호출한다. "누구를 때릴지" 개념 자체가 없다.
- **카드에 "아군 대상"이라는 범주가 없다.** `battle_scene.gd:1202` `_targets_an_enemy()`가 카드를
  "적 하나를 겨냥" / "그 외(자기 자신)" 둘로만 가른다. 아군 힐/버프는 표현할 자리가 없다.
- **아군 스프라이트가 단일 노드로 박혀 있다.** `battle_scene.gd:687` `_player_sprite`(`$View/Actors/PlayerSprite`)를
  연출 코드가 **64곳**에서 직접 참조한다. HUD도 `PlayerCard` 하나(초상화/HP바/마나바/골드) 고정.
- **반대로 적 진영엔 다개체 machinery가 이미 있다.** `_setup_sprites()`가 0번 슬롯을 템플릿 삼아
  `_clone_sibling()`(`:2688`)으로 복제하고, `_layout_actors()`가 배치를 계산하며, HUD 카드도 같은 방식으로 늘어난다.
  **아군 쪽에 같은 패턴을 이식하는 건 "없는 걸 발명"이 아니라 "있는 걸 복제"에 가깝다.**

### 1-3. 자원 경제는 철저히 1인용으로 설계돼 있다

이건 코드 난이도와 별개로 **게임 디자인상 가장 큰 제약**이다:

- 손패 5장(`HAND_SIZE`), 마나 풀 하나(`GameState.flags.player_mana`), 무기 과열 게이지(`WeaponState`,
  검/지팡이 각각 0~100, 턴당 전환 3회 제한) — 전부 "한 명이 한 턴에 무엇을 할지 고민한다"를 전제로 튜닝돼 있다.
- 덱은 `StarterDeck.build()`가 `GameState.unlocked_cards` / `battle_deck`에서 만든다. 덱 구성 상한 15장,
  같은 카드 2장 제한(`MAX_BATTLE_DECK_SIZE`, `MAX_COPIES_PER_CARD`).

→ **동료가 같은 마나/손패를 쓰면 그건 사실상 "카드가 몇 장 늘어난 것"이고**(= 아래 B안),
**동료가 독립 자원/독립 턴을 가지면 이 경제 전체를 다시 튜닝해야 한다**(= C안). 이 갈림길이 옵션을 가른다.

### 1-4. NPC / 대화 시스템은 이미 충분히 표현력이 있다

- `npc/npc.gd`(258줄) 베이스 + 캐릭터별 서브클래스(`yusuf_npc.gd` 등). 서브클래스는 `_ready()`에서
  `dialogue_tree` / `dialogue_start_id` / `met_flag_name` / 스프라이트만 지정하면 끝.
- 상태에 따라 첫 대사를 갈아끼우는 훅이 이미 있다 — `_resolve_start_id()`
  (예: `yusuf_npc.gd`는 엘라라를 만나기 전이면 `yusuf_locked_greeting`으로 분기).
- 대화 노드 어휘도 풍부하다 — `show_if_flag`(23곳), `set_flag_on_show`(13), `required_affinity`(9),
  `show_if_seen`/`show_if_not_seen`, `text_by_affinity_tier`(5), `give_gift`(7).
- 호감도(`GameState.affinity`, 0~100, tier: cold/neutral/warm/trusted)와 초상화(`dialogue_box.gd:41` `PORTRAITS`)도
  이미 유서프 항목을 갖고 있다.

→ **"동료의 신뢰도/유대"를 새로 만들 필요가 없다. 기존 호감도를 그대로 쓰면 된다.**

### 1-5. 오버월드 동행: 따라다니는 패턴의 선례가 있다

플레이어는 `SceneManager`가 들고 있는 영속 노드다(`scene_manager.gd:67` `_player`). 씬이 바뀔 때마다
`_attach_player_to_scene()`(`:202`)가 ① Y-Sort 씬이면 씬 밑으로, 아니면 SceneManager 밑으로 재부모화하고
② z_index를 캐릭터 밴드에 맞추고 ③ 그 씬의 ShadowLayer에 그림자를 다시 붙인다.

→ 따라다니는 동료를 만든다면 **이 함수가 그대로 청사진**이다(같은 재부모화 + 그림자 + z밴드).
새로 발명할 게 아니라 한 벌 더 만드는 일에 가깝다.

### 1-6. 세이브: flags에 얹으면 공짜

`systems/save_manager.gd:33-49`는 GameState의 필드를 납작한 딕셔너리로 통째 저장한다(`flags`, `affinity`,
`inventory`, `unlocked_cards`, `battle_deck` …). 그리고 `restore_flags()`(`game_state.gd:274`)는
**기본값으로 리셋 후 덮어쓰기** 방식이라 구버전 세이브에 없는 키는 자동으로 기본값이 된다
(`player_base_max_hp` 마이그레이션이 그 선례).

→ 동료 상태를 `flags`에 넣으면 **세이브/로드/하위호환 코드를 한 줄도 안 건드려도 된다.**
별도 최상위 키로 빼더라도 `restore_affinity` 같은 기존 패턴을 그대로 따라가면 된다.

## 2. 옵션

### A안 — 스토리 동행자 (현행 방식의 공식화)

**개념**: 동료는 전투에 등장하지 않는다. 씬마다 배치된 NPC로 존재하고, "지금 누가 동행 중인가"만
상태로 관리해 대사/컷신/연출이 그걸 참조한다. 지금 Part 2가 이미 하고 있는 방식에 이름을 붙이는 것.

**구현 방식**
- `GameState.flags`에 `companion_yusuf`(또는 `active_companion: String`) 추가 → 세이브 자동 처리.
- 각 씬에 유서프 NPC 인스턴스를 배치하고, 서브클래스의 `_resolve_start_id()`로 진행 상황별 대사 분기
  (이미 `yusuf_desert_npc.gd`가 하는 그대로).
- (선택) 오버월드에서 실제로 따라다니게 하려면 `_attach_player_to_scene()` 패턴을 본뜬 follower 노드 1개 추가.

**손대는 범위**: `npc/` 서브클래스 몇 개, `dialogue_data.gd` 대사 추가, flags 1개. **전투 코드 0줄.**

| | |
|---|---|
| 장점 | 리스크 거의 없음. 밸런스 영향 0. 이미 검증된 패턴. 대사 콘텐츠에 100% 집중 가능 |
| 단점 | 전투에 들어가면 동료가 사라진다 — "끝까지 같이 가자"고 해놓고 보스전은 혼자. 서사·연출 괴리가 가장 큰 안 |
| 난이도 | **낮음** (follower까지 하면 중하) |

---

### B안 — 전투 보조자 (효과로만 참여) ★ 권고안

**개념**: 동료에게 독립 HP/개체를 주지 않는다. 대신 전투에 **효과와 존재감으로만** 참여한다.
플레이어는 여전히 유일한 조작 주체이고, 동료는 "플레이어를 강화하는 무엇"으로 표현된다.

**구현 방식** (아래를 조합, 전부 다 할 필요 없음)
1. **동료 전용 카드 주입** — `StarterDeck.build()`가 동행 중일 때 유서프 카드 n장을 덱에 섞는다.
   카드 데이터는 기존 `.tres` 그대로라 **새 시스템이 사실상 없다.** 카드 이름/연출만 유서프 것으로.
2. **패시브 1개** — 예: 전투당 1회, HP 0이 될 때 1로 버티며 유서프가 끼어드는 연출.
   `battle_turn_manager.gd`의 `_resolve_single_attack`/`_finish_battle` 근처에 훅 하나.
3. **지원 게이지/버튼** — 턴 종료 버튼 옆에 동료 행동 버튼 1개(쿨다운/횟수 제한).
   내부적으로는 "카드 없이 즉발 효과 1회"라 기존 효과 적용 경로를 재사용.
4. **화면 존재감** — 플레이어 옆에 유서프 스프라이트를 세우고(장식), 특정 타이밍에 대사 한 줄.
   `_player_sprite` 옆에 노드 하나 추가하는 수준 — 타겟 대상이 아니므로 64곳을 건드릴 필요가 없다.

**손대는 범위**: `starter_deck.gd`(주입 분기), `battle_turn_manager.gd`(훅 1~2개),
`battle_scene.gd`(장식 스프라이트 + 버튼 1개), 카드 `.tres` 추가, flags 1개.
**건드리지 않는 것: 타겟팅 규칙, 적 공격 대상 선정, 플레이어 상태 구조, 세이브 포맷.**

| | |
|---|---|
| 장점 | 전투 화면에 동료가 실제로 존재하면서, 1인용 자원 경제(손패/마나/과열)를 전혀 흔들지 않음. 밸런스 조정이 카드 수치라 쉽고 되돌리기도 쉬움. A안 위에 증분으로 얹힘 |
| 단점 | 진짜 파티 전투는 아님 — 동료는 맞지 않고, 죽지 않고, 지켜야 할 대상도 아니다. "전술적으로 동료를 운용한다"는 맛은 안 남 |
| 난이도 | **중** (1번만 하면 중하) |

### C안 — 완전한 파티 멤버

**개념**: 유서프가 독립된 전투 개체가 된다. 자기 HP를 갖고, 적에게 맞고, 쓰러질 수 있고,
아군 대상 카드(힐/버프)의 대상이 된다.

**구현 방식 — 선행 리팩터링이 먼저다**
1. **플레이어 개체 추출** — 지금 없는 `PlayerState`(또는 공용 `CombatantState`)를 만들어야 한다.
   `MonsterState`가 좋은 본보기. 저장은 계속 `GameState.flags`가 하더라도, 전투 중에는 개체 객체를 경유하게.
   영향: `battle_turn_manager.gd`의 GameState 참조 28곳 + `battle_scene.gd` 25곳.
2. **피격 대상 일반화** — `_resolve_single_attack()`이 "누구를 때릴지" 고르게 바꾼다
   (지금은 `GameState.damage_player()` 직결). 어그로/타겟 선정 규칙도 새로 정해야 한다.
3. **아군 타겟 범주 신설** — `_targets_an_enemy()`의 2분류를 적/자신/아군 3분류로 확장하고,
   타겟 선택 UI(`_begin_targeting` 계열)가 아군 스프라이트도 클릭 대상으로 인식하게.
4. **아군 다개체 연출** — `_player_sprite` 64개 참조를 슬롯 배열로 정리. 적 진영의
   `_clone_sibling` + `_layout_actors` 패턴을 아군에 이식.
5. **규칙 신설** — 동료 사망/기절, 부활, 동료 사망 시 패배 여부, 경험치/보상 분배, 동료 장비 유무.
6. **자원 결정** — 동료가 같은 마나/손패를 쓰는가(→ 사실상 B안), 아니면 독립 자원인가(→ 전투 밸런스 전면 재튜닝).
7. **세이브** — 동료 HP/상태 저장 + 구버전 호환.

| | |
|---|---|
| 장점 | 유일하게 "파티 JRPG"의 맛이 나는 안. 지켜야 할 동료, 아군 힐, 동료 사망 같은 서사적 장치를 전투 규칙으로 표현 가능 |
| 단점 | 범위가 압도적으로 크고, 전투 밸런스를 처음부터 다시 잡아야 한다(적 피해량이 단일 대상 전제로 튜닝됨). 카드 게임의 핵심 재미(손패 5장·마나·과열의 1인 최적화)가 희석될 위험 |
| 난이도 | **높음** — 이번 프로젝트에서 지금까지 한 어떤 작업보다 큼 |

## 3. 비교표

| | A안 동행자 | B안 보조자 | C안 파티 멤버 |
|---|---|---|---|
| 전투 등장 | ✗ | 장식 + 효과 | 독립 개체 |
| 적에게 맞는가 | ✗ | ✗ | ○ |
| 아군 힐/버프 대상 | ✗ | ✗ | ○ |

## 4. 권고

**A → B 순서로 증분 진행하고, C는 "정말 파티 전투 게임을 만들 것인가"를 먼저 결정한 뒤에만.**

이유:
1. **A는 이미 사실상 구현돼 있다.** Part 2 유적 시퀀스가 그 방식으로 굴러가고 있어, 공식화 비용이 거의 0이다.
2. **B가 서사 괴리를 가장 싸게 메운다.** "끝까지 같이 가자"의 다음 전투에서 유서프가 화면에 서 있고
   그의 카드가 손에 들어오는 것만으로도 동행감은 상당히 채워지는데, 전투 규칙의 근간은 그대로다.
3. **C의 상당 부분은 결국 B로 수렴한다.** 동료가 같은 마나/손패를 공유하는 설계라면, 기계적으로는
   "카드가 늘어난 것" 이상이 아니다. C가 B와 **실제로** 달라지는 건 동료가 독립 자원·독립 턴을 가질 때뿐이고,
   그건 이 게임이 튜닝해 온 1인 카드 경제를 다시 설계하는 일이다.
4. B까지 해두면 C로 가는 길이 막히지 않는다. 아래 준비 항목만 지켜두면 된다.

### C를 언젠가 할 생각이라면, 지금 싸게 해둘 준비

이건 A/B를 하면서 곁다리로 지켜두면 나중 비용이 크게 줄어드는 것들이다(지금 당장 할 필요는 없음):

- 플레이어 HP/마나 변경을 항상 `GameState`의 헬퍼(`damage_player`/`heal_player_*`/`spend_mana`)로만 하기 —
  이미 대체로 지켜지고 있다. 직접 `set_flag("player_hp", …)` 하는 경로를 늘리지 않는 것만으로 충분.
- `battle_scene.gd`에서 새 연출을 쓸 때 `_player_sprite`를 직접 박기보다 "행위자 스프라이트를 돌려주는
  접근자"를 한 번 거치게 하기 — 64곳을 더 늘리지 않는 것이 목표.
- 새 카드 효과를 추가할 때 `_targets_an_enemy()`의 분류에 반드시 등록하기(이미 그렇게 주석에 적혀 있음) —
  나중에 3분류로 넓힐 때 누락이 안 생긴다.

## 5. 결정이 필요한 열린 질문

1. **동료는 전투에서 죽을 수 있어야 하는가?** "예"면 C안 외엔 답이 없다. "아니오"면 B안으로 충분하다.
2. **동료가 여럿이 될 가능성이 있는가?** (카밀/나딤 등) 1명 전제면 B안이 훨씬 싸고, 다수 전제면
   C안의 개체 추출을 처음부터 하는 게 낫다.
3. **동료의 강함을 플레이어가 키우는가?** (동료 레벨/장비/전용 덱) "예"면 C안 + 별도 성장 UI가 필요하다.
4. **유서프의 "신뢰도"를 기존 호감도로 쓸 것인가, 별도 축으로 뺄 것인가?**
   기존 `GameState.affinity["yusuf"]` 재사용이 압도적으로 싸다(대사 게이팅 어휘가 이미 다 있음).
5. A안 이상을 택한다면 `part1_story_script_draft.md:620`의 결정문과 `yusuf_desert_npc.gd:7`의 주석을
   함께 갱신할 것 — 안 그러면 다음 사람이 상반된 두 문서를 보게 된다.

## 6. 결정 (2026-09-06 확정 — C안 채택)

기존 "동료 불필요" 결정(0번 섹션의 `part1_story_script_draft.md:620`, `yusuf_desert_npc.gd:7`)을 번복하고
**C안(완전한 파티 멤버)**을 채택한다. 단 아래 확정 스펙은 사용자가 직접 제시한 조건이라 원안과 세부적으로
다른 지점이 있다 — 특히 "동료를 플레이어가 조작하지 않는다"는 결정이, C안이 원래 필요하다고 봤던
카드 타겟팅 3분류 확장(적/자신/아군, `_targets_an_enemy()` 개편)을 없애준다. 플레이어 카드는 여전히 적만 타겟.

### 확정 스펙
- **최종 파티 규모**: 플레이어 포함 최대 4인(엘라라/로한/유서프/플레이어). 단 Part 2 기준 실질 최대는
  플레이어+유서프 2인 — 나머지는 Part 3/4 이후를 위한 확장성 확보 목적.
- **필드 동행**: 동료는 합류 즉시 기존 배치형 NPC에서 사라지고, 플레이어를 따라다니는 팔로워로 전환된다.
  플레이어가 멈춰서 상호작용 키를 누르면 "동료와 대화" 옵션이 뜨고, 기존 `dialogue_tree`를 그대로 재사용한다.
- **전투 합류 인원**: 적이 1~3명 랜덤으로 채워지는 것과 동일한 방식으로, 아군도 최대 4명까지 채워진다.
- **전투 조작 모델**: 동료는 플레이어가 조작하지 않는다(변신도, 지시도 아님). 플레이어는 자기 캐릭터만
  관리하고, 동료는 매 턴 자동으로 적을 공격하며, 캐릭터별 고유 패시브(자동 발동)/액티브(플레이어가 특정
  키로 발동, 쿨다운 있음)를 가진다.
- **HP**: 플레이어와 각 동료는 개별 HP를 갖는다(공유 아님).
- **패배 조건**: 플레이어 HP가 먼저 0이 되어도 즉시 패배가 아니다 — 플레이어는 "다운(관전, 부활 없음)"
  상태가 되고, 살아있는 동료가 있으면 전투가 계속된다. **파티 전원(플레이어+동료) HP가 0이 돼야 패배.**
- **유서프 능력 초안**:
  - 패시브: 5턴마다 1회, 플레이어에게 소량 마나 또는 체력 회복.
  - 액티브: 플레이어가 특정 키로 발동, "마력장벽" — 다음 턴 받는 데미지 방어/경감. 쿨다운 있음(수치 미정).

### 아직 안 정해진 것 (구현 전 확인 필요)
- 동료의 강함을 플레이어가 성장시키는가(레벨/장비/전용 카드 등)? — 5번 섹션 질문 3, 아직 미답변.
- 유서프의 "신뢰도"를 기존 호감도(`GameState.affinity`)로 쓸지 별도 축으로 뺄지 — 5번 섹션 질문 4,
  아직 미답변(원안 권고: 기존 호감도 재사용이 압도적으로 쌈).
- 유서프 액티브 스킬 쿨다운/수치, 패시브 회복량 구체적 수치.
- 적 AI가 플레이어와 동료 중 누구를 때릴지 고르는 규칙(완전 랜덤 vs 가중치).
- 다운된 플레이어를 되살릴 수단은 이번 스코프에 없음 — 부활 아이템/스킬은 미래 스코프로 명시적으로 제외.

### 구현 로드맵 (`project-jrpg-handoff.md`에도 동일하게 기록)
Phase 0(문서 동기화, 진행 중) → Phase 1(백엔드 골격: `CompanionState` 클래스 신설, 플레이어 쪽 리팩터링
범위 판단 — **Opus 설계 권장**) → Phase 2(필드 동행: 팔로워 노드 + "동료와 대화" 인터랙션 — Sonnet) →
Phase 3(전투 통합: 피격 대상 일반화, 아군 다개체 연출, 매 턴 자동행동+패시브 트리거, 액티브 스킬,
"파티 전원 HP 0" 패배 판정 — **Opus 설계 후 Sonnet 구현**) → Phase 4(유서프 전용 패시브/액티브 구현 —
Sonnet) → Phase 5(미래: 엘라라/로한 추가, 4인 파티 스케일링 — 지금은 스펙만 열어두고 손 안 댐).
