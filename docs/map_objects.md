# 맵 오브젝트 프리팹 가이드

> 작성일: 2026-08-23
> 첫 사례: `world/tree_prop.gd` (마을 나무)
> 두 번째 사례: `world/vegetation_prop.gd` (마을 식생 — 크기별 충돌 분기 + 타일→프리팹 전환)
> 세 번째 사례: `world/rock_prop.gd` (마을 바위 — 흔들리지 않는 오브젝트, 바닥 발자국 충돌)
> 그림자: `world/shadow_layer.gd`(공용 레이어·광원 방향), `world/character_shadow.gd`(플레이어/NPC)

플레이어를 가리기도, 가려지기도 해야 하는 맵 오브젝트(나무, 바위, 건물 등)를
새로 만들 때 따라야 할 구조를 정리한다. 이 문서가 정하는 규칙을 지키면
Y-Sort/충돌/정렬이 다른 캐릭터·오브젝트와 자동으로 맞는다. 어기면 "충돌은
되는데 항상 뒤에 그려진다", "가까이 가면 갑자기 사라진다" 같은, 원인을
한눈에 알기 어려운 버그가 난다 — 실제로 나무를 만들며 두 개 다 겪었다
(아래 "왜 이렇게 정하는가"에 기록).

## 요약 (체크리스트)

새 오브젝트 프리팹을 만들 때:

1. 씬 파일이 아니라 **스크립트가 조립**하게 한다 (모델/변종이 여럿이면 표로).
2. 루트 노드는 물리적 장애물이면 `StaticBody2D`, 아니면 `Node2D`.
3. **노드 원점(position 0,0)을 오브젝트의 "발밑"(바닥과 닿는 지점)에 둔다.**
   스프라이트는 원점에서 위로 그리고, 충돌 모양은 원점 근처의 좁은 영역에만 둔다.
4. 캐릭터와 섞여야 하면(플레이어가 앞을 지나갈 수 있어야 하면):
   - 부모가 `y_sort_enabled = true`인 씬에 있어야 한다.
   - `z_index = SceneManager.CHARACTER_BAND_Z_INDEX`를 준다.
5. 바닥에 서 있는 것이면 **그림자**를 준다 (7장) — 스프라이트를 검게 복제해
   `ShadowLayer.lay_on_ground()`로 눕히고, `ShadowLayer.adopt()`로 공용 레이어에 맡긴다.
6. 실제로 게임을 켜서 확인한다: 오브젝트 뒤에서 앞으로 걸어보고, 밑동이
   막히는지, 그 위(지붕/캐노피 등)로는 지나갈 수 있는지.

## 1. 원점 = 발밑

캐릭터(플레이어/NPC)는 스프라이트가 **중심 기준(centered)**이라, 노드
원점이 발보다 한참 위(허리~가슴 높이)에 있다. 반면 맵 오브젝트는 원점을
**발밑(바닥에 닿는 가장 아래 지점)** 에 두는 것이 규칙이다. 이렇게 갈리는
이유는 Y-Sort가 "노드의 global_position.y"만 비교하기 때문이다 — 둘 다
발밑을 기준으로 잡아야, 두 오브젝트가 화면상 같은 높이(같은 y)에서 겹칠
때 "실제로 발이 닿아 있는 순서"대로 자연스럽게 앞뒤가 갈린다. 한쪽만
중심 기준이면 그 오브젝트는 자기 몸통 절반만큼 앞당겨(혹은 늦춰) 정렬되어
버려서, 발밑이 아니라 허리 높이에서 앞뒤가 뒤바뀌는 부자연스러운 지점이
생긴다.

스프라이트는 `centered = false`로 두고 `offset`을 `(-width/2, -height)`로
줘서, 원점(0,0)이 스프라이트의 가로 중앙·세로 맨 아래에 오도록 그린다.

```gdscript
_sprite.centered = false
_sprite.offset = Vector2(-region.size.x / 2.0, -region.size.y)
```

### SORT_BIAS — 캐릭터와 정확히 맞추려면 한 걸음 더

위 규칙대로 "그림의 맨 아래 = 원점"으로 두면 이론적으로는 맞지만,
실제로 캐릭터 스프라이트를 만들 때 발끝이 정확히 캔버스 맨 아래 픽셀에
붙어 있지 않은 경우가 많다(신발 밑에 여백이 조금 있다든지). 그래서 나무
프리팹은 정렬 기준점을 "그림 맨 아래"보다 `SORT_BIAS`(20px)만큼 위로
올려서, 실측으로 캐릭터와 맞을 때까지 조정할 여지를 남겼다. 새 오브젝트를
만들 때도 처음엔 0으로 시작해서, 실제로 캐릭터를 오브젝트 옆으로 걸려보며
어긋나면 이 값을 조정하는 식으로 잡는 걸 권장한다 — 숫자를 계산으로
미리 맞추려 하지 말 것 (동굴 어둠 셰이더 반경을 정할 때도 그랬듯, 이런
"감으로 맞춰야 하는" 수치는 렌더링해보고 정하는 게 더 빠르고 정확하다).

## 2. 충돌 모양 = 좁게, 발밑 근처에만

스프라이트 전체(캐노피/지붕까지)를 덮는 충돌을 주면, 그림보다 훨씬 넓은
범위에서 막혀 버려 어색하다. 나무는 줄기 밑동만, 바위는 바위가 실제로
땅에 닿는 밑변만, 건물은 벽 라인만 — **그림에서 실제로 "딱딱한 부분"만**
`CollisionShape2D`로 잡는다.

```gdscript
var shape := RectangleShape2D.new()
shape.size = Vector2(maxf(region.size.x * TRUNK_WIDTH_RATIO, TRUNK_WIDTH_MIN), TRUNK_HEIGHT)
_collision.shape = shape
_collision.position = Vector2(0.0, -TRUNK_HEIGHT / 2.0)  # 원점(발밑) 바로 위
```

`StaticBody2D`가 이 프로젝트의 첫 물리 장애물 노드였다 — 그전까진
`Area2D`(상호작용 감지)만 있었고, 실제로 플레이어를 막는 콜라이더가
없었다. 새 장애물도 이 패턴(`StaticBody2D` + `CollisionShape2D`)을
따르면 된다.

## 3. Y-Sort 컨테이너 조건

Y-Sort는 "같은 부모 밑의 형제"끼리만 정렬한다. 그래서 오브젝트가 캐릭터와
섞이려면 두 가지가 다 맞아야 한다:

1. **부모 씬에 `y_sort_enabled = true`가 켜져 있어야 한다.** (`world/village.tscn`의
   루트 `Village` 노드처럼. 지금은 마을만 켜져 있다 — 동굴/숲/사막은 아직
   Y-Sort를 안 쓰는 고정 z_index 방식이라 이 규칙이 적용되지 않는다.)
2. **z_index가 캐릭터와 같아야 한다.** Y-Sort보다 z_index 비교가 먼저
   일어나기 때문에, z_index가 다르면 y좌표는 아예 비교되지 않는다.
   이 프로젝트에서 "캐릭터와 섞여야 하는 것"의 공통 z_index는
   `SceneManager.CHARACTER_BAND_Z_INDEX`(5)로 정해뒀다 — 새 오브젝트도
   이 상수를 그대로 쓴다. 직접 숫자를 적지 말 것(나중에 밴드 값이
   바뀌면 여기도 같이 바뀌어야 하는데, 상수를 안 쓰면 놓치기 쉽다).

```gdscript
z_index = SceneManager.CHARACTER_BAND_Z_INDEX
```

### 왜 z_index가 필요한가 (배경)

타일맵 데코 레이어(돌·풀 등)가 z_index 1~4를 쓰고 있다. 처음 나무를
z_index 0으로 뒀을 때, 데코 레이어의 돌 타일이 나무와 플레이어를
전부 덮어버리는 게 실제로 발견됐다 — 렌더링해보기 전까진 안 보이는
문제였다. 그래서 "서로 앞뒤를 가려야 하는 대상"은 전부 데코보다 위,
그 안에서는 y좌표로 경쟁하는 밴드(z=5)에 모아두기로 했다.

플레이어도 마찬가지로, Y-Sort 씬에 들어갈 때는 이 밴드로 z_index가
바뀐다(`SceneManager._attach_player_to_scene()` 참고). Y-Sort를 쓰지
않는 씬에서는 `PLAYER_OVERLAY_Z_INDEX`(10)로 돌아가 항상 배경 위에
그려진다 — SceneManager가 오토로드라 배경 씬보다 먼저 그려지기 때문에,
그 씬에서는 z_index로 강제로 앞에 놔야 한다.

### 오토로드가 들고 있는 노드는 씬 밑으로 옮겨야 한다

플레이어는 `SceneManager`(오토로드)가 소유해서 기본적으로 씬 트리
바깥에 있다 — Y-Sort 대상 형제가 될 수 없다. 그래서 Y-Sort 씬에
들어갈 때는 실제로 그 씬의 자식으로 재부모화한다(`_attach_player_to_scene`
/ `_detach_player_from_scene`). 새로운 종류의 "오토로드가 들고 있으면서
Y-Sort에도 참여해야 하는" 노드를 또 만들게 되면 같은 패턴이 필요하다.

## 4. 변종이 여러 종류면 표로 관리 (스크립트가 조립)

나무처럼 같은 종류의 오브젝트가 여러 모양(모델/사이즈)으로 존재하면,
`.tscn` 파일을 모양 수만큼 만들지 않는다. `monster_encounter.gd`가 몬스터
변종을 고르는 방식을 그대로 따라, **씬 하나 + 변종 표(Dictionary) + `variant`
export 변수** 구조로 만든다:

```gdscript
const VARIANTS: Dictionary = {
	"key": {"sheet": "res://...png", "region": Rect2(x, y, w, h)},
	...
}

@export var variant: String = "":
	set(value):
		variant = value
		if is_node_ready():
			_build()
```

인스턴스는 `.tscn`을 `instance=ExtResource(...)`로 찍고 `variant = "key"`만
지정하면 된다 — 스프라이트 잘라내기, 충돌 크기 계산 등은 전부 `_build()`가
공통으로 처리한다.

## 5. (선택) 정적 장식에 살랑임 등 절차적 움직임을 주고 싶다면

별도 애니메이션 프레임 없이, `canvas_item` 셰이더의 `vertex()`에서
`UV.y`를 기준으로 흔들림 정도를 가중치 주면 충분하다(`world/foliage_sway.gdshader`
참고) — 위쪽일수록 많이, 아래쪽(뿌리/바닥)일수록 거의 안 움직이게. 머티리얼
하나를 모든 인스턴스가 공유해도 `MODEL_MATRIX`에서 월드 좌표를 뽑아 위상을
어긋나게 하면 각자 다르게 흔들린다(인스턴스별 머티리얼 복제 불필요).

### ⚠ 타일 레이어에 흔들림 셰이더를 걸 때의 함정

"타일맵에 이미 찍혀 있는 장식(풀 등)에 흔들림만 얹고 싶다"는 생각이 먼저 들지만,
이 프로젝트에서 실제로 확인한 결과 **타일 쪽에는 이 셰이더를 그대로 쓸 수 없다.**
두 가지 별개의 문제가 있다.

**(1) 범위 문제 — 레거시 `TileMap`에는 레이어별 머티리얼이 없다.**
`TileMap`(레거시)은 노드 전체가 `CanvasItem` 하나이고 `layer_N/material` 같은
속성이 없다. 즉 거기에 머티리얼을 걸면 **그 타일맵의 모든 레이어(땅·벽·지붕·돌까지)
가 전부 흔들린다.** 범위를 좁히려면:
- `TileMapLayer` 노드(각각이 `CanvasItem`이라 자체 머티리얼 가능)로 분리하거나,
- `TileData.material`로 타일별 머티리얼을 지정한다.

**(2) 더 근본적인 문제 — 타일 셰이더에는 "오브젝트" 개념이 없다.**
범위를 좁혀도 흔들림 자체가 깨진다. 이 sway는 "스프라이트 하나 = 오브젝트 하나"라서
`UV.y`가 곧 그 오브젝트 안에서의 높이(위=0, 아래=1)라는 전제 위에 성립한다.
타일맵에서는 UV가 **칸 단위로 끊기기** 때문에, 여러 칸에 걸친 오브젝트(3x3 덤불 등)는
칸마다 독립적으로 기울어져 **칸 경계마다 그림이 어긋나 찢어진다.** 셰이더 안에서는
"이 픽셀이 속한 오브젝트의 밑동이 어디인지"를 알 방법이 없어서 우회도 안 된다
(`fract(VERTEX.y / 16.0)` 같은 꼼수도 결국 칸 경계에서 불연속이 생긴다).

**결론:** 흔들려야 하는 장식이 **한 칸짜리뿐이면** 타일 레이어 분리로도 되지만,
**두 칸 이상에 걸친 오브젝트가 하나라도 있으면 프리팹으로 빼는 쪽이 맞다.**
마을 식생은 60여 개 중 3분의 1이 2~3칸짜리라 프리팹 전환을 택했고, 그 김에
크기별 충돌 분기(아래 6번)도 같이 해결됐다.

## 6. 같은 종류인데 크기에 따라 충돌을 다르게 줘야 한다면

변종 표에 `blocks` 같은 불리언을 넣고, `_build()`에서 그 값에 따라
`CollisionShape2D`를 만들거나 만들지 않는다(`world/vegetation_prop.gd` 참고).

```gdscript
const VARIANTS: Dictionary = {
	"bush_0_6_3x3": {"region": Rect2(0, 96, 48, 48), "blocks": true},
	"plant_0_11_1x1": {"region": Rect2(0, 176, 16, 16), "blocks": false},
}
```

타일셋에 충돌을 넣으면 "타일 = 칸"이라 크기와 무관하게 16x16 정사각이 붙기 쉬운데
(마을 식생이 실제로 그 상태였다 — 잔풀 한 포기가 벽처럼 앞을 막았다),
프리팹으로 빼면 오브젝트 단위로 "막을지 말지"와 "얼마나 좁게 막을지"를
따로 정할 수 있다.

## 7. 그림자

바닥에 서 있는 것에는 전부 그림자를 준다. 없으면 오려 붙인 스티커처럼 붕 떠 보인다.
방식은 두 가지이고, **모양이 고정인지 아닌지**로 갈린다.

- **맵 오브젝트(나무/식생/바위): 스프라이트를 그대로 복제한 실루엣.**
  같은 texture/region을 쓰는 두 번째 `Sprite2D`를 만들어 `modulate = Color(0,0,0,1)`로
  칠한다. 변종마다 모양이 달라도 그림자가 알아서 그 실루엣을 따라가고,
  크기 비율을 따로 계산할 필요도 없다.
- **캐릭터(플레이어/NPC): 납작한 타원 폴리곤** (`world/character_shadow.gd`).
  캐릭터는 매 프레임 팔다리 모양이 바뀌어서, 실루엣을 바닥에 깔면 그림자가 같이
  펄럭여 시선을 끈다. 전투 화면(`battle_scene.gd`의 `_setup_shadow`)과 같은 방식이다.

### 광원 방향은 맵 전체가 하나만 쓴다

에셋(Rocks/Trees/Vegetation)이 전부 오른쪽 면을 어둡게 칠해둔 = **왼쪽 위에서 빛이 오는**
그림이다. 그래서 그림자는 전부 오른쪽 아래로 눕는다. 값은
`ShadowLayer.GROUND_LEAN`(높이 1당 오른쪽 이동 = 0.40)과
`ShadowLayer.GROUND_SQUASH`(높이 1당 아래쪽 이동 = 그림자 길이 = 0.45) 둘뿐이고,
**오브젝트별로 다르게 주면 안 된다** — 하나만 어긋나도 "빛이 두 군데서 온다"로 보인다.
(0.20/0.22, 0.30/0.34, 0.30/0.50, 0.45/0.50을 같은 화면에 나란히 렌더링해 비교하고 고른 값)

눕히는 일은 `ShadowLayer.lay_on_ground(shadow, art_offset, foot_y)`가 다 한다.
캐릭터 타원은 `ShadowLayer.ground_shift(높이)`로 중심만 같은 방향으로 민다.

#### ⚠ 함정 1 — 위로 눕히면 그림자가 오브젝트 뒤로 숨는다

세로로 납작하게 누르기만 하면(= y축 부호를 그대로 두면) 그림자가 밑동에서 **화면 위쪽**으로
뻗는다. 그런데 화면 위쪽은 "더 먼 곳"이고 그 자리에는 오브젝트 그림 자신이 서 있어서,
그림자가 통째로 그 뒤에 가려 **아무것도 안 보인다**. 실제로 이렇게 만들어놓고 한참
"CanvasGroup이 안 그려지나"를 의심했다. 바닥 변환은 y축을 **뒤집어야** 한다
(`ShadowLayer.ground_transform()`이 열 벡터 `(-LEAN, -SQUASH)`로 그렇게 되어 있다).

#### ⚠ 함정 2 — 발밑을 축으로 눕혀야 하는데, 원점은 발밑이 아니다

`Node2D`의 변환은 노드 원점을 축으로 돈다. 그런데 정렬 기준점 때문에 원점은 발밑보다
`SORT_BIAS`만큼 **위**에 있다. 그대로 눕히면 그림자 밑동이 발에서 떨어져 붕 뜬다.
그렇다고 원점을 발밑으로 내리면 이번엔 흔들림 셰이더가 어긋난다 — 위상을 `MODEL_MATRIX`의
위치에서 뽑기 때문에, 스프라이트와 원점이 달라지는 순간 둘이 다른 박자로 흔들린다.
그래서 원점은 그대로 두고 `offset`만 보정한다:
`offset = art_offset − F + M⁻¹·F` (F = 발밑). `lay_on_ground()`가 이미 이렇게 되어 있다.

### 겹쳐도 진해지지 않게: 공용 `ShadowLayer` (CanvasGroup)

반투명 검정을 여러 장 겹치면 겹친 부분만 알파가 곱해져 유독 진하게 뭉친다
(0.28 두 장 = 약 0.48). 그래서 모든 그림자를 **하나의 `CanvasGroup`** 밑에 모으고,
자식은 전부 **불투명**(alpha=1) 검정으로 그린 뒤 반투명함은 그룹의
`self_modulate.a`(=`SHADOW_ALPHA` 0.28) 하나로만 준다. 그룹이 오프스크린 버퍼에 먼저
합성한 뒤 알파를 한 번만 입히므로 몇 장이 겹쳐도 밝기가 똑같다.

- 그림자는 일단 자기 노드의 자식으로 만든 뒤 `ShadowLayer.adopt(shadow, self)`로 넘긴다
  (전역 위치를 보존하며 재부모화하고, 레이어가 아직 없으면 몇 프레임 기다렸다 다시 찾는다).
- 레이어 `z_index`는 `SceneManager.SHADOW_LAYER_Z_INDEX`(= 캐릭터 밴드 − 1)로 고정.
  y좌표와 무관하게 항상 캐릭터/나무 아래, 데코 타일 위에 깔린다.
- **그림자를 갖는 오브젝트는 캐릭터 밴드(z=5)에 있어야 한다.** 그보다 낮은 z에 두면
  자기 그림자가 자기 위에 그려진다. (마을 식생 42개가 옛 타일 레이어의 z를 그대로
  물려받아 z=0~4에 있다 — 그림자가 아래로 눕는 지금은 자기 몸과 거의 겹치지 않아
  눈에 띄지 않지만, 새로 만드는 것은 처음부터 밴드에 맞출 것.)

측정으로 확인하는 법: 흔들림 셰이더를 끄고 트리를 `paused = true`로 멈춘 뒤(안 그러면
NPC 배회·HUD 때문에 프레임마다 달라진다) 빈 풀밭에 큰 그림자 둘을 겹쳐 놓고
A만/B만/A+B/없음 4장을 찍어 `both == min(A, B)`인지 픽셀로 비교한다. 실제로 이 방법으로
겹친 15,489픽셀 전부에서 편차 0.000000을 확인했다.

## 예시로 따라가기

`world/rock_prop.gd`가 이 문서를 그대로 따라 만든 세 번째 사례다. 요약하면:

1. `world/rock_prop.gd` (`class_name RockProp extends StaticBody2D`) 생성.
2. 바위 텍스처가 여러 크기/모양이면 `VARIANTS` 표 + `variant` export.
3. `_ready()`에서 `z_index = SceneManager.CHARACTER_BAND_Z_INDEX`.
4. `_build()`에서 스프라이트를 `centered = false` + 아래쪽 정렬로 배치,
   바위 밑변에만 작은 `CollisionShape2D`.
5. 그림자 스프라이트를 만들어 `ShadowLayer.lay_on_ground()` + `ShadowLayer.adopt()`.
6. `world/rock_prop.tscn`으로 감싸고, Y-Sort가 켜진 씬(현재는 `village.tscn`)에
   인스턴스로 배치.
7. 실행해서 플레이어가 바위 뒤/앞으로 지나갈 때 자연스러운지, 바위 밑변만
   막히는지 확인.

바위에서 나무와 달랐던 점 두 가지:

- **흔들림 셰이더를 붙이지 않는다.** 바위가 살랑이면 곤란하다.
- **충돌이 "밑동"이 아니라 "바닥 발자국"이다.** 나무는 줄기만 가늘게 막으면 되지만
  (잎 아래로는 지나다녀야 한다), 바위는 덩어리째 땅에 놓여 있어 아랫부분을 넓게 막는다
  (`BASE_WIDTH_RATIO` 0.8 × `BASE_DEPTH_RATIO` 0.33). 그래도 타일이던 시절처럼
  그림 전체(32x48)를 막지는 않는다 — 위쪽을 뒤로 지나갈 수 있어야 Y-Sort가 의미를 갖는다.
- **정렬 기준점을 크기로 나눴다.** 돌아서 가는 바위는 나무와 같은 `SORT_BIAS` 20,
  밟고 지나가는 작은 돌은 잔풀과 같은 8 (`PEBBLE_SORT_BIAS`).

### 너무 작은 것은 프리팹으로 옮기지 않는다

바위 타일 60칸 중 22칸은 불투명 픽셀이 8~36개뿐인(≈6x4px) 먼지 같은 조각이라
타일로 그냥 뒀다. 그 크기에서는 28% 알파 그림자가 사실상 안 보이고, 노드만 22개 늘어난다.
불투명 픽셀 72개(≈12x9px) 이상인 작은 돌 10칸은 옮겼고, 실제로 그림자가 또렷하게 보인다.
**옮길지 말지는 "칸 수"가 아니라 시트에서 잰 불투명 픽셀 수로 판단할 것.**

## 부록: 타일맵에 이미 찍힌 것을 프리팹으로 옮길 때 (마이그레이션 절차)

나무·식생·바위 셋 다 원래는 타일이었고, 옮기는 과정에서 아래 절차를 지켰다.
타일 데이터는 바이너리로 인코딩돼 있어 눈으로 검토할 수 없으므로, 손대기 전에
**왕복 검증**을 먼저 하는 것이 핵심이다.

> 재사용 가능한 변환 **도구는 아직 없다**. 세 번 다 그때그때 파이썬 스크립트를 짜서
> 돌리고 버렸다(리포지토리에 `.py`가 하나도 없는 이유). 네 번째가 생기면 그때
> 도구로 승격하는 게 낫겠지만, 지금까지는 오브젝트마다 묶는 규칙이 달라서
> (나무=원점 기준, 바위=아틀라스 좌상단 기준) 공통화 이득이 크지 않았다.

1. `world/village.tscn`을 백업해 둔다.
2. `layer_N/tile_data`(레거시 `TileMap`, `PackedInt32Array`)를 디코드 →
   그대로 재인코딩했을 때 **원본 문자열과 바이트 단위로 일치**하는지 확인한다.
   (3개 int32 = 12바이트 = uint16 6개: x, y, source_id, atlas_x, atlas_y, alternative.
   `TileMapLayer`의 `tile_map_data`는 base64이고 2바이트 헤더 + 타일당 12바이트로 다르다.)
   일치하지 않으면 인코딩 이해가 틀린 것이므로 거기서 멈춘다.
3. 같은 오브젝트에 속한 타일을 묶는다. 공간 인접(8방향)으로 묶으면 **붙어 있는 두
   오브젝트가 하나로 합쳐지므로**, `원점 = (맵좌표 − 아틀라스좌표)`로 묶는 게 정확하다
   (같은 스탬프에서 나온 타일끼리만 원점이 같다). 묶은 결과가 꽉 찬 직사각형이 아니면
   우연히 원점이 겹친 별개 타일이므로 칸 단위로 쪼갠다.
4. 옮길 타일만 `tile_data`에서 빼고, 같은 자리에 프리팹 인스턴스를 넣는다.
   제거한 타일 수가 예상과 정확히 일치하는지 확인한다.
5. 검증할 때는 **흔들림 셰이더를 잠시 꺼두고** 이전/이후 스크린샷을 픽셀 비교한다
   (안 그러면 흔들림 때문에 전부 다르게 나와 의미 있는 비교가 안 된다).
   화면이 통째로 밀려 보이면 대개 카메라(=플레이어) 위치가 달라진 것이니,
   정렬 오프셋을 찾아 맞춘 뒤 잔차를 본다 — 식생 작업 때 실제로 겪었는데,
   잔풀 충돌을 없앤 덕에 플레이어가 더 이상 밀려나지 않아 생긴 차이였다.
